# 2026-10-09 ~ 10-11 两网故障复盘与应对方案

覆盖两次事故（主网 bell 落库超时、cali 快照缺块）、一次两网共患（富豪榜停更）
与一条长期未治的病根（mongo 读放大）。**原则：数据不能丢、数据必须正确**——
补齐可以是事后的，但正确性必须是最终的、可验证的。

## 二、根因（四个，按可控性排序）

### A. cali：快照导入的块存储有洞

决定性证据（2026-10-11 08:48 实测）：

```
badger vlog 000000~000005.vlog 全部 Dec 24 2025   ← 快照导入，之后没补过
lotus 1.37.0+calibnet，uptime 08:48:58，从未跑 import-chain
lotus.log: could not find = 939,345 条（14.6 万 distinct CID）
公网 filfox 对同批 CID 全部 ChainHasObj=true       ← 链上有，本地没有
```

**这不是 splitstore 裁剪历史（那是预期行为），而是快照本身不完整**：
6 棵状态树共 84 个节点缺失（命中高度 4140561/4141154/4141280/4141349/4141401/4141444）。

特征：**不可自愈**（节点不会自己补）、**有洞就必炸**（碰到即整批失败）、
且**下次炸哪是随机的** ⇒ 属于需要主动排查而非等告警的类型。

### B. 两网共患：mongo 读放大（2026-10-11 实测复核）

**主机与盘（本次核实，read-only）**

| | cali | 主网 |
|---|---|---|
| 机型 | `r6i.large`（2 核 / 15 GB） | `m7g.4xlarge`（16 核 / 61 GB） |
| mongod RSS | 11.5 GB | 44.9 GB |
| 数据盘 | 800 GB **gp3**（16,000 IOPS / 1,000 MB·s⁻¹） | 2000 GB **gp3**（16,000 IOPS / 1,000 MB·s⁻¹） |
| 数据量 | — | **1.4 TB**（`/mongo-data`，69% 用量） |

⇒ **技能里「EBS 被改成 sc1/st1」那条病因本次排除**：两网都是 gp3，且 16,000 IOPS 额度远高于实测的 1,500–2,200 r/s。

**慢查询日志（主网 `/root/logs/mongod.log`，阈值 100 ms）**

| 指标 | 实测 |
|---|---|
| 当日条数 | 102,779（前一日 126,620） |
| 分布 | **p50 = 436 ms，p90 = 922 ms，max = 1,907,951 ms（≈31.8 分钟）** |
| 耗时去向 | **`timeReadingMicros` 合计 74,703 秒；`timeWritingMicros` 合计 0 秒** ⇒ **慢在读** |
| Top namespace | `bell.ActorAddress` 156,403 / `bell.ActorState` 31,011 / `bell.ActorBalance` 23,960 |
| `ActorBalance` 单集合 | 15,590 次调用、565 万条文档、48,052 秒，其中 **42,478 秒是读** |

**两个被本次实测推翻/新增的判断**

1. **不是事故期专属，是长期稳态**：10-05 有 131,222 条、10-06 有 46,318 条、10-09 有 153,600 条
   （须用 `zgrep` 读 `.gz`，用 `grep` 会一律读到 0 —— 本次踩过这个坑）。
2. **大部分慢查询是「什么都没插进去」的空转写**：`bell.ActorAddress` 60,607 次慢查询里
   **59,985 次 `ninserted:0`**，每次耗时 ~433 ms、返回 820 KB 的重复键错误；
   `ActorBalance` 的 `ninserted` p50 也是 0。⇒ 存在大量**重复写入**在持续消耗 mongo。

**尚未取得（需 mongo 认证，本次未拿到凭据）**：WiredTiger cache 实际配置值、
各集合索引数（`nindexes`/`keysInserted`）。这两项决定「扩 cache」还是「减索引」哪条更对症，
是下一步要补的取证。


### C. 放大器：失败的影响范围 = 整批

```
6 个坏块 → 3487 个高度全作废 → 31.5 小时
1 个 part 超时 → 2053 个高度全作废 → 16.6 小时
```

实测的讽刺之处：主网那次 **`done-parts=128/129`**——99.2% 的工作做完，因最后一个失败全部作废。

### D. 代码闸门 + 上游竞态（富豪榜）

旧版 `actor_balance_task.go`：

```go
currentDay := chain.CurrentEpoch().CurrentDay()
if currentDay == ctx.Epoch() { ... }   // lockstep：游标只会「越过」，永不重试
```

两个因素叠加导致永久断档：

1. **闸门**：游标逐个高度前进，只在恰好等于日边界那一刻进分支；
2. **窗口期竞态**：跨边界那一刻上游 `ActorBalance@Epoch==边界` 在 mongo 尚未落盘
   ⇒ 聚合器返回空 ⇒ `warn + return`。等数据落齐（约 1~2 小时）游标已越过边界，本期永久丢失。

`f2f2aa4`（`==` → `>=` + 回库存在性检查）**只治第 1 条，未治第 2 条**。

## 五、数据正确性验收（本次复盘补做）

原则要求「最终数据正确」而不只是「恢复」。cali 实测（2026-10-11 08:48）：

| 校验 | 结果 |
|---|---|
| `miner_infos` 恢复区间整点行数 | 12 行/整点连续，无断层 |
| `actor_actions` 洞前后行数 | 1499 / 1424 —— 同量级，无断层 |
| `builtin_actor_states` 同 epoch 行数 | 4140600/4141000/4141300 各 2 行 —— **幂等、无重复写入** |

⇒ 本次恢复既完整又幂等，未出现「有行但全零」的空壳。
**此验收应固化为每次洞类事故的收口必做项**，而不是靠临场想起来。

## 六、方法论教训（给下一个处理同类故障的人）

1. **「批次原子性」不是可权衡的产品偏好**，它由数据正确性决定。想缩短故障时长，
   要动的是「失败影响范围」，不是「提交粒度」。
2. **判"是不是偶发可自愈"必须跨多次采样**。本次两次误判都源于单次采样：
   bell「日志静默 11 分钟」被我判成死锁（实际 21 分钟后自行恢复）；
   miner 指针倒退被我判成卡死（实际 15 分钟后自己越过毒点追平）。
3. **告警的实时性不可信**。本次 `filscan根因形态出现` 的 30 分钟窗读数从 3 次到 4 次失败
   期间一个字节没变，一直重放旧通知；数值判断一律以现测为准。
4. **上线前必须现探线上二进制版本**。本次据 GitHub commit 状态断言「主网未部署 f2f2aa4」，
   实测主网 10-10 就已部署——差点导致一次无谓的生产停机。
